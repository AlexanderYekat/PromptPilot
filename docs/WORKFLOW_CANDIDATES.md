# Фиксация версии кода при приёмке workflow

Функция включается до запуска workflow: в форме создания или настройках отметьте
«фиксировать версию кода при приёмке». Эквивалент в API:

```json
{
  "candidate": {
    "enabled": true,
    "additional_inputs": ["requirements.md"],
    "output_directories": ["_local/results"]
  }
}
```

Это фрагмент `config`. По умолчанию функция выключена. Старые workflow и
импортированные PASS остаются прежними; миграция только добавляет таблицы и не
запускает задачи. Включение не утверждает план и не запускает benchmark.

## Передача результата

До постановки исполнителя в очередь сервер фиксирует корень checkout, общий Git
каталог, ветку, исходный commit, опись файлов и дополнительные документы. Папка
резервируется в БД: другой задаче PromptPilot нельзя выдать работу в ней или
пересекающемся каталоге до завершения приёмки. Перед фактическим запуском worker
повторяет проверку. Изменившаяся очередь не становится новой исходной версией.

Исполнитель получает обязательный контракт и завершает отчёт отдельной строкой:

```text
CANDIDATE_JSON: {"candidate_revision":"<полный Git commit SHA>","no_changes":false}
```

SHA должен совпадать с HEAD указанного checkout. Для этапа без изменений:
исходный SHA и `no_changes:true`; пустой commit не нужен. Исполнитель сам получает
SHA через Git. Переменная в окружении и SHA в произвольном тексте не принимаются.
Внешний исполнитель возвращает такую же строку в `result` запроса
`POST /api/workflows/{id}/external-result`; запись связана с конкретным внешним
`executor_run_id`, а `executor_task_id` в этом случае равен `null`.

Сервер проверяет ветку, существование commit, ancestry от исходного commit,
разрешённые пути этапа и отсутствие незакоммиченного кода. Запись кандидата
создаётся в одной транзакции с переходом к gate. `candidate_id` уникален;
`executor_run_id` уникален в таблице, UPDATE/DELETE запрещены триггерами.
Повторная синхронизация не создаёт вторую запись. Новая доработка создаёт новую
передачу; предыдущие версии и протоколы сохраняются.

## Входы и результаты

Все отслеживаемые файлы проверяются по commit и SHA-256 фактических байтов;
`assume-unchanged`, `skip-worktree` и `.gitignore` не освобождают исходники от
проверки. Неотслеживаемые файлы, включая игнорируемые, блокируют сдачу, кроме
явно указанных документов и выходных каталогов.

Дополнительные входы — конкретные документы `.md`, `.txt`, `.rst`, `.pdf`,
указанные относительно корня репозитория. Их содержимое и исходное состояние
индекса сохраняются. Они могут содержать существующие изменения пользователя;
исполнитель не должен их менять или включать в свой commit. Код, конфигурацию и
тесты нужно коммитить. Это намеренно ограниченный первый вариант дополнительных
входов; не используйте исключения для зависимостей, исходников или тестов.

Выходные каталоги должны быть отдельными, без отслеживаемых файлов и входных
документов. Укажите только каталоги генерируемых результатов, например
`_local/results`, `.pytest_cache`, `tests/__pycache__`. Виртуальное окружение и
средства запуска удобнее разместить вне checkout. Нельзя исключить корень
репозитория, `tests` или `src`; исходники внутри выходных каталогов также блокируют сдачу.
Symlink, submodule и пользовательские Git clean filters в проверяемых входах пока
блокируются. PromptPilot не выполняет reset, clean, stash или автокоммит.

## Gate и аудит

На каждый процесс gate сервер устанавливает отдельное окружение, перекрывая
унаследованные значения:

- `PROMPTPILOT_CANDIDATE_SHA` — сохранённый полный SHA;
- `PROMPTPILOT_CANDIDATE_ID` — ID передачи результата;
- `PROMPTPILOT_CANDIDATE_REPOSITORY` — канонический абсолютный путь checkout.

Команда запускается из сохранённого checkout. Пример для Windows PowerShell:

```powershell
& 'C:/Tools/Python/python.exe' './scripts/gate.py' --expected-revision "$env:PROMPTPILOT_CANDIDATE_SHA" --repository "$env:PROMPTPILOT_CANDIDATE_REPOSITORY" --no-model
```

В поле команды обратных слешей перед кавычками **нет**. При передаче через JSON
кавычки экранируются стандартным JSON-сериализатором. В POSIX shell используются
`"$PROMPTPILOT_CANDIDATE_SHA"` и `"$PROMPTPILOT_CANDIDATE_REPOSITORY"`.

Перед и после каждой команды проверяются версия и входы. Exit code 0 при
изменённых входах не даёт PASS. Протокол хранит candidate_id, ожидаемую и
наблюдаемую версии, команду, cwd, exit code и результат проверки целостности.
Обнаруженная потеря целостности необратимо аннулирует эту сдачу: возвращение
файлов назад не восстанавливает старые PASS.

Аудитор получает полную запись и протоколы gate в `run.input`; в промпте —
идентичность сдачи, протоколы и ссылку на API полного манифеста.
Шаблоны поддерживают `{{candidate_revision}}` и
`{{candidate_repository_path}}`. Папка и входы проверяются перед запуском,
после завершения аудитора и при применении решения. Принимается только PASS
самого аудитора с теми же findings и успешными обязательными gate этой сдачи,
без открытых blocker/high. Запоздалые ответы остаются в истории и не меняют
текущий раунд.

## API и восстановление

- `GET /api/workflows/{id}/candidates` — неизменяемая история сдач с полными SHA и манифестами.
- `GET /api/workflows/{id}/candidate-readiness` — проверка настроек и использования переменных без запуска команд.
- `POST /api/workflows/{id}/gate/run` с `{"expected_version":N}` — явный запуск обязательных проверок в ручном workflow.
- Обычные JSON и Markdown экспорты включают сдачи; полные протоколы доступны в событиях и JSON экспорте.

Фиксация версии и контракт gate не меняются после начала исполнения. План,
который использует переменные кандидата без включения механизма, нельзя утвердить.
Планировщик получает информацию о наличии механизма. Карточка показывает SHA,
папку, состояния gate/аудита и причину блокировки.

Начало gate записывается **до** запуска процесса. После сбоя или конкурентного
вызова тот же запуск не повторяется автоматически и не считается успешным.
Оператор проверяет последствия и через Resume начинает новую передачу результата
и проверки. Код, inputs и доказательства предыдущей сдачи остаются в истории.
Такой путь не разрешает автоматически повторять измерительные обращения к моделям.

## Границы первой реализации

Исполнитель, gate и аудитор должны использовать один локальный checkout.
Роли с `worktree:true`, удалённой машиной или существующей `herdr-session`
блокируются заранее; их настройки не отключаются молча. Свежие локальные
CLI-процессы запускаются с сохранённой рабочей папкой. Для внешнего исполнителя
версия проверяется по той же папке в момент передачи результата.

Проверка до и после не защищает от кратковременной записи сторонней программой
между проверками. Это контроль целостности общей папки, а не неизменяемая среда.
Для усиленной изоляции нужен отдельный подготовленный checkout и ограничения
записи. Локальная БД и окружение самого оркестратора относятся к доверенной части
системы; пользователь, имеющий к ним прямую запись, может менять состояние.

Регрессионные проверки: `python -m pytest tests/test_workflow_candidates.py -q`.
Они используют временные Git-репозитории и локальные тестовые процессы; платные
провайдеры и benchmark не запускаются.
