## Окружение и запуск

Выбран Python 3.12. Для новой установки:

```powershell
py -3.12 -m venv .venv312
.\.venv312\Scripts\python.exe -m pip install -e ".[dev]" -c ci/requirements-ci.txt ruff==0.16.9
.\tools\check-custom.ps1
.\tools\start-custom.ps1
```

На подготовленном компьютере `.venv312` уже создана; Python 3.10/3.12
расположены в `_local/python`. Переносить эти окружения в другую папку нельзя.

Запуск создаёт **отдельный неизменяемый снимок коммита** в `_local/releases/<sha>`.
Данные находятся в `_local/data`, конфигурация в `_local/trial.env`, журналы в
`_local/logs`, идентификация версии в `_local/trial-release.json`.
Интеграция в основном дереве не меняет код работающего снимка.
Перед сменой снимка скрипт автоматически сохраняет согласованную копию SQLite,
остальных данных, trial.env и указателя версии в `_local/backups/`.
`PP_ENV_FILE` запрещает подмешивание рабочей `.env` из домашнего каталога;
унаследованные `PP_*` очищаются только в процессе запуска, затем восстанавливаются.

По умолчанию запускаются server и локальные маршруты. Worker не запускается.
Первичная очередь приостановлена. Для осознанного запуска настоящих агентов:

```powershell
.\tools\stop-custom.ps1
.\tools\start-custom.ps1 -Worker
# Затем нажмите «Продолжить» для worker в интерфейсе, проверив очередь.
```

Это расходует квоту вашего CLI. После первого Resume состояние очереди сохраняется:
повторный запуск с `-Worker` может продолжить задачи. Без `-Worker` агентские
задачи останутся в очереди. Telegram-бот не запускается.

Остановка: `tools/stop-custom.ps1`. Скрипт проверяет PID, время запуска и путь
кода, затем останавливает только дерево процессов стенда. `-WhatIf` показывает план.
Повторный запуск сохраняет историю. Порт 8421 должен быть свободен.
Проверка времени процесса учитывает преобразование ISO-дат в PowerShell 7.

CLI с той же изолированной конфигурацией:

```powershell
.\tools\custom-cli.ps1 workflow external demo-external
.\tools\custom-cli.ps1 workflow submit demo-external --text "Мой результат" --performer "Имя" --comment "Версия 1"
.\tools\custom-cli.ps1 flows items
```

## Попробовать функции

1. В Workflow откройте `demo-external`. Он уже ожидает внешнего результата.
   Скопируйте задание, подготовьте инструкцию и сдайте результат с именем
   исполнителя и комментарием. Сдача создаёт задачу независимому reviewer Codex
   с правами `read`. До явного запуска worker ревью ждёт в очереди.
   После замечаний сдайте исправленную версию. Только PASS завершает работу.
2. В «Заявках» откройте локальную заявку `demo-local`: настоящая локальная
   команда уже посчитала слова, решение человека завершает или отклоняет заявку.
   Можно создать новую заявку через UI или CLI. Писем, issues и сетевых действий
   в этом маршруте нет. Это демонстрация маршрута без подставных AI-ответов.
3. При создании задачи выберите провайдера и «Права». Claude поддерживает
   `none/read/write/full`; Codex — `read/write/full`, `none` отклоняется.
   В CLI: `add "Задание" -c codex --rights read`; при ручной отправке роли:
   `workflow dispatch <id> executor "Задание" -c codex --rights read`.

Полный цикл automatic → external → revision → PASS → automatic проверяется
автотестом `test_workflow_external.py`; ответы агентов там подставные и не являются
живой приёмкой CLI. Живая приёмка требует отдельного явного запуска агентов.
Установленные CLI при обследовании: Codex 0.154.0, Claude Code 2.1.288, herdr 0.9.1.
Проверка `--help` и построения команды не доказывает фактическое ограничение процесса.
Codex `workspace-write` разрешает команды внутри песочницы. Claude `write`
ограничивает список инструментов, исключая Bash. Это разные модели ограничений.

Примеры реальных коннекторов: [FLOWS.md](FLOWS.md) и `docs/examples/flows/`.
Подключение почты/GitLab требует ваших адресов, параметров маршрутизации и локальных
секретов. Не помещайте их в Git.

## Сопровождение

Проверка источников без изменения рабочего дерева:

```powershell
.\.venv312\Scripts\python.exe tools/fork_status.py --fetch
```

Скрипт проверяет remote, принятую историю выбранных веток и текущие состояния PR.
`--offline` предназначен только для диагностики, поскольку не проверяет PR.
Если новых коммитов и состояний нет, тесты не повторяются и уведомление не нужно.

При обновлении создаётся кандидат `integrate/<дата>` от последнего custom в
свободной отдельной рабочей копии. Сначала merge upstream/main, затем только
поддерживаемые ветки из манифеста. Изменения читаются и проверяются; конфликт
или упавшая проверка оставляют custom и запущенный снимок на прежней версии.
Принятые автором PR снимаются с сопровождения только после сверки итогового поведения.
Другие функции можно предлагать, автоматически включать их нельзя.

Публикация кандидата и продвижение после CI:

```powershell
.\tools\check-custom.ps1
git push origin integrate/<дата>
.\.venv312\Scripts\python.exe tools/promote_custom.py integrate/<дата> --evidence _local/evidence/local-check.json
```

Продвижение требует квитанцию локальной проверки **этого же SHA** и шесть успешных
заданий Tests: Windows/Linux × Python 3.10/3.12, ruff, JavaScript. Перед атомарным
push снова читаются origin и upstream. Продвижение только fast-forward, прежний
custom сохраняется отдельной archive-веткой. Ручной force-push запрещён.
Чистый main синхронизируется fast-forward; при расхождении требуется разбор истории.

По уточнению пользователя от 4 октября 2026 выбран **Планировщик Windows,
только проверка и уведомление**. Ежедневного запуска модели и автоматической
интеграции больше нет: Codex пользователь запускает сам при найденных изменениях.

Задание `PromptPilot-CheckUpdates`: ежедневно в 10:00 по локальному часовому поясу
Windows `Ekaterinburg Standard Time` (Asia/Yekaterinburg). Проверяющий скрипт
использует стандартную библиотеку Python и публичный GitHub API без ключей.
Он читает манифест опубликованного `origin/custom`, сравнивает upstream/main,
вершины выбранных веток и состояния PR. Снимок скрипта лежит отдельно в
`_local/maintenance/runtime`; смена ветки разработки не меняет его.

```powershell
.\tools\install-update-check.ps1 -RunNow
Get-ScheduledTaskInfo -TaskName PromptPilot-CheckUpdates
Get-Content _local\maintenance\last-check.json
# Отключить проверку:
Disable-ScheduledTask -TaskName PromptPilot-CheckUpdates
```

При новых изменениях появляется окно Windows на 60 секунд, а готовое задание
для Codex сохраняется в `_local/maintenance/pending.md`. При ошибке API/сети
появляется уведомление об ошибке; это не считается отсутствием обновлений.
Одинаковое состояние повторно не уведомляет; при отсутствии изменений проверка
молчит. `last-check.json` хранит результат и время, `checker-error.json` — ошибку
самого проверяющего процесса, если она возникнет. LastTaskResult должен быть 0.

Для выполнения нужны включённый компьютер, вход пользователя в Windows и сеть;
приложение Codex и подписка для проверки не нужны. Сон не прерывается принудительно;
пропущенный запуск обрабатывается Планировщиком при доступности условий.
Если компьютер или сеть долго недоступны, проверку нужно выполнить вручную.
После ручного изменения часового пояса переустановите расписание.
Квота Codex потребуется только для вручную начатого разбора обновлений.
Публикация custom по-прежнему не развёртывает обновление на рабочие данные.

## Перенос и откат

Основная установка находится в `C:\MyProjects\workflow-pilot\PromptPilot`, её
данные — в `C:\MyProjects\workflow-pilot\local-data`. Автоматически она не обновляется.
На отдельной копии её базы проверена миграция с сохранением всех 95 задач и
существующих пользовательских строк; отчёт — `_local/evidence/production-copy-migration.json`.
Копия никогда не подключается к worker.

После приёмки стенда перенос делается отдельным этапом: проверить активные задачи,
приостановить и остановить службы, сохранить согласованный комплект базы через
SQLite backup, конфигураций и точной версии кода, проверить миграцию новой копии,
запустить из отдельного снимка и проверить историю. Нужные секреты копируются только
локально. Исходные материалы `update-20260928/` и `моё-предложение-фитча.md`
не включаются автоматически в коммиты.

Откат: остановить службы, сохранить неудачную версию для разбора, восстановить
**согласованную пару старый код + резервная база и настройки**, затем запустить и
проверить историю. Возврат только к старому Git-коммиту не откатывает схему SQLite.
Для стенда действуют те же правила: `_local/releases` хранит код, `_local/backups`
содержит автоматически созданные копии перед сменой снимка. Проверяйте наличие
нужной копии и восстанавливайте данные только при остановленных службах.
