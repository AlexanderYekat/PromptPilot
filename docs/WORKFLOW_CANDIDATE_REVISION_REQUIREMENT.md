# Требование к фиксации версии кода при приёмке workflow

Статус: к реализации в линии `custom` форка `AlexanderYekat/PromptPilot`.
Дата: 2026-10-10.

## Зачем это нужно

Исполнитель, автоматические проверки и независимый аудитор должны работать с одной переданной на приёмку версией кода. PromptPilot должен сам фиксировать эту версию, передавать её проверкам и связывать с ней результаты. Пользователь не должен вручную вводить Git SHA или переменные окружения перед каждым этапом.

Пример ожидаемого поведения: исполнитель сдаёт версию A; тесты проверяют A; аудитор проверяет A. Если до окончания приёмки появилась версия B или изменились проверяемые файлы, результаты для A нельзя использовать для принятия B.

## Исходная проблема

В плане `cost-benchmark-pilot` команды этапов требуют `--expected-revision` со значением из `PROMPTPILOT_CANDIDATE_SHA`. Само упоминание переменной в плане не создаёт механизм её заполнения. В проверенном релизе `cf1263983051fa661eb2fba41418285095685481` формирование этой переменной в коде workflow и worker не обнаружено.

План находится на утверждении. Это требование описывает доработку PromptPilot; оно само по себе не меняет настройки, не утверждает план и не запускает исполнение.

## 1. Передача результата исполнителем

Перед запуском исполнителя PromptPilot сохраняет исходную идентичность репозитория, рабочую папку, ветку, текущий commit и опись допускаемых существующих пользовательских изменений.

По окончании этапа исполнитель передаёт результат с машиночитаемым полем `candidate_revision`: полный идентификатор Git commit. Изменения реализации и тестов, предъявляемые к приёмке, должны входить в этот commit. Для этапа без изменений допустим прежний commit при явно зафиксированном отсутствии изменений; создавать пустой commit не требуется.

PromptPilot независимо проверяет через Git:

- commit существует в нужном репозитории и соответствует фактическому HEAD сдаваемой рабочей папки;
- ветка соответствует кандидату workflow, а история не подменена относительно зафиксированной исходной версии;
- код реализации и проверок не содержит незакоммиченных изменений или незарегистрированных исходных файлов;
- изменения не выходят за разрешённый объём этапа; существующие пользовательские файлы сохранены.

Нельзя считать доказательством только текст «готово», SHA в произвольном тексте отчёта или значение переменной, которое прислал агент. Отсутствие корректной структурированной передачи результата блокирует начало приёмки с понятной причиной.

## 2. Запись версии на стороне PromptPilot

После проверки PromptPilot атомарно создаёт неизменяемую запись передачи результата с уникальным `candidate_id`. В ней должны быть:

- workflow, этап, раунд и конкретная задача исполнителя;
- идентичность репозитория, канонический абсолютный путь рабочей папки и ветка;
- исходный commit и `candidate_revision`;
- манифест проверяемых файлов и разрешённых дополнительных входов с контрольными суммами;
- время фиксации и версия состояния workflow.

Запись хранится в данных оркестратора и доступна в API и экспорте. Она не должна существовать только как изменяемый файл в репозитории, которым управляет исполнитель.

Один результат задачи обрабатывается идемпотентно: повторная синхронизация не создаёт вторую передачу результата. Для следующей доработки создаётся новая запись; предыдущие записи и протоколы не переписываются.

## 3. Передача версии автоматическим проверкам

Перед каждым запуском gate PromptPilot берёт ожидаемую версию из сохранённой записи передачи результата и задаёт в окружении дочернего процесса:

- `PROMPTPILOT_CANDIDATE_SHA` — проверенный полный Git commit;
- `PROMPTPILOT_CANDIDATE_ID` — идентификатор конкретной передачи результата;
- `PROMPTPILOT_CANDIDATE_REPOSITORY` — канонический путь сдаваемой рабочей папки.

Эти значения задаются только для конкретного запуска. Их нельзя хранить в глобальном окружении, общей `.env` или повторно использовать между независимыми workflow. Значения из окружения родителя или конфигурации пользователя не могут переопределить зафиксированную версию.

Gate запускается из сохранённой рабочей папки. Перед запуском и после завершения PromptPilot проверяет HEAD, состояние проверяемых файлов и неизменность входов. Ожидаемый SHA нельзя заново вычислять из текущего HEAD непосредственно перед проверкой: иначе изменение кода будет незаметно принято за новую норму.

Для Windows проверить передачу через фактически используемый запуск PowerShell. Шаблон аргумента `--expected-revision "$env:PROMPTPILOT_CANDIDATE_SHA"` должен передавать программе один непустой SHA без лишних обратных слешей и кавычек. Проверить пути с пробелами и кириллицей.

В протокол gate записываются `candidate_id`, ожидаемая и наблюдавшаяся версии, рабочая папка, команда, код завершения и результаты проверки целостности. Успешный exit code не означает PASS, если версия или проверяемые файлы изменились.

## 4. Независимый аудит и окончательная приёмка

Задача аудитора получает ту же запись передачи результата и протоколы gate с тем же `candidate_id`. В промпте и API задачи явно доступны версия и путь; для шаблонов добавить документированные поля `{{candidate_revision}}` и `{{candidate_repository_path}}`.

PromptPilot проверяет соответствие рабочей папки и версии до запуска аудитора, после его завершения и перед применением итогового решения. Совпадение SHA в тексте ответа аудитора само по себе не заменяет эту проверку.

Принять этап можно только при успешных обязательных gate и вердикте аудитора PASS, относящихся к одной действующей записи передачи результата, без неразрешённых блокирующих замечаний. Запоздалый ответ аудитора для предыдущего раунда сохраняется в истории, но не принимает новую версию.

После изменения кода требуются новая передача результата и новые проверки. Нельзя переиспользовать PASS другой версии, даже если названия этапа и команды совпадают.

## 5. Рабочая папка и существующие изменения

Одинаковый commit не гарантирует одинаковые файлы: незакоммиченные и неотслеживаемые изменения должны учитываться отдельно. Проверяемый код и тесты после сдачи должны соответствовать commit; исходные документы пользователя допускаются только как заранее явно описанные дополнительные входы с проверенными контрольными суммами.

Не добавлять пользовательские изменения в commit автоматически и не выполнять reset, clean, stash или принудительное переключение ради получения «чистой» папки. Если безопасно зафиксировать результат невозможно, остановить приёмку с перечнем мешающих файлов.

Создаваемые проверками журналы и результаты разрешены только в заранее указанных выходных каталогах. Нельзя исключать из контроля весь репозиторий или папку с тестами под видом служебных результатов. Изменение любого входа, в том числе документа с требованиями, требует новой фиксации результата.

На время приёмки PromptPilot не должен выдавать другому своему исполнителю работу, изменяющую ту же папку. Проверка до и после не является полной защитой от кратковременной записи сторонней программой; пользовательский режим совместного редактирования нельзя объявлять неизменяемой средой. Для усиленной изоляции нужен отдельный подготовленный checkout с ограничениями записи.

В первой реализации допустима поддержка единой рабочей папки для всех ролей. Если исполнитель находится в worktree, а gate или аудитор направлены в другую папку, запуск приёмки блокируется заранее. Автоматическое перенаправление всех ролей между worktree — отдельная возможность; это требование не должно молча отключать пользовательскую настройку worktree.

## 6. Ошибки и восстановление

Различать отсутствие переданной версии, неподходящую рабочую папку, изменение кода после сдачи, обычное падение тестов и замечания аудитора. Пример сообщения: «Код изменился после передачи на проверку. Сдайте новую версию; предыдущие результаты сохранены».

При ошибке нельзя молча подставлять текущий HEAD, переходить на проверку другой папки или объявлять этап принятым. Повтор проверки той же версии допустим по действующим правилам workflow только после повторной проверки её идентичности; новые измерительные обращения к модели автоматически не разрешаются.

После перезапуска worker использовать сохранённую запись. Повторно проверить её актуальность до продолжения. Частично выполненные gate не считать успешными, незавершённый аудит не считать PASS. Одновременная синхронизация и запоздалые события не должны принимать устаревший результат.

## 7. Интерфейс и совместимость

В карточке этапа показывать: переданную версию, рабочую папку, состояние автоматических проверок и аудита, а также конкретную причину остановки. Сокращённый SHA пригоден для отображения; полный SHA и `candidate_id` должны быть доступны в подробностях и экспорте.

Настройку фиксации версии включать явно для workflow. Старые workflow и их история должны оставаться читаемыми; прежние PASS без записи версии не превращаются в доказанную приёмку конкретного commit. Не запускать старые задачи повторно при миграции.

Если план использует `PROMPTPILOT_CANDIDATE_SHA`, до его утверждения проверять, включён ли и поддерживается ли механизм передачи версии. При его отсутствии показывать конкретный блокер. Обновить инструкции планировщику: он не должен предполагать поддержку несуществующего механизма.

## 8. Критерии приёмки реализации

Проверить автоматическими тестами на временных Git-репозиториях и тестовом provider, без платных обращений к моделям:

1. Исполнитель сдаёт commit A; все gate и аудитор получают A и один `candidate_id`; после успешных проверок этап принимается.
2. После сдачи HEAD сменился на B: gate не запускается на B под видом A, старый PASS не применяется.
3. HEAD остался A, но изменён файл кода, тест, дополнительный вход или добавлен незарегистрированный исходник: приёмка блокируется.
4. Gate вернул 0, но изменил проверяемый файл: PASS не выдаётся. Запись в разрешённый каталог результатов сама по себе проверку не ломает.
5. Версия отсутствует, не существует, относится к чужому репозиторию или другой задаче: получен понятный отказ до запуска проверки.
6. Два параллельных workflow получают разные значения окружения; унаследованный старый SHA не подменяет ожидаемый.
7. Аудитор завершился после новой сдачи: его ответ не принимает новую версию. Изменение файлов во время аудита также препятствует приёмке.
8. Перезапуск worker и повторная синхронизация сохраняют идентичность сдачи и не создают дублей или ложного PASS.
9. Несовпадение рабочей папки исполнителя, gate и аудитора обнаруживается до проверки, включая случай одинакового HEAD в разных checkout.
10. Существующие пользовательские изменения сохраняются; исключения по файлам явные и проверяемые; старые workflow читаются без переоценки истории.
11. Реальный дочерний процесс PowerShell получает правильный SHA и пути с пробелами/кириллицей; проверка не ограничивается mock окружения.
12. Для плана `cost-benchmark-pilot` проверка готовности подтверждает совместимость команд с передачей версии без запуска самого benchmark.

Результат реализации: код, миграция при необходимости, регрессионные проверки, обновлённая документация и пример команды gate. Прохождение проверок кандидата и публикация в `custom` выполняются по `AGENTS.md` форка. Создание этого требования не является разрешением на утверждение плана или запуск пилота.
